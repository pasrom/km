# Evals

One case per row of the dispatch table in `skills/km/SKILL.md`, plus a negative case. Each case scaffolds a brain with `km init` from this checkout (`lib/brain.sh`), so run with `--scaffold`; the write and shell cases need `--allow-tools Bash Write Edit`, and every shell command then runs in Claude Code's sandbox inside the fixture brain. That sandbox has no network and gives the run its own empty home, so `lib/brain.sh` installs a uv-managed Python with `bin/km`'s PyYAML pin into that home before the session (this step needs uv and network): `bin/km` then starts offline on its first call. Without it, a run spends its turns getting km to start. The step stands in for what a user's first run fetches from the network, so a passing eval does not show that `bin/km` starts in a sandbox without network.

Each case whose row names a reference file has a `reads-reference` grader (that file was read); `help` and `save content` name only the core, so they have none. `save-cites` is a second case of the save row: a note that links a SharePoint file with a synced copy at hand, which the save flow cites with `km cite add` before the commit. `save-generated` is a third: a note with an SVG plotted from a local measurement export, which the save flow commits together with the script that draws it and a line on how to regenerate it. Its fixture brain lacks the rule in CONVENTIONS.md, like a brain set up before it, so the case measures the skill alone; the model mostly keeps the script without the plugin too (baseline 0.67 and 1.00 in two runs), so it guards against a regression rather than showing a lift. Every case has one grader on the flow's key step (the `km` command it runs, the file it writes, the line it answers). Graders are `tool_used` and `regex`, except the `llm` graders in `fix-in-mounted-brain` and `save-generated` (the latter judges the trace, not the reply).

A grader on a `km` command (`runs-km-*`) checks that km ran, not how the model typed it: it is a `regex` on the `trace` that matches a line km itself prints (`repin: <doc> pins ...`, `km doctor: <root>`, `ERRORS: <n>`, ...) at the start of a line of a tool result. The model calls km as `km`, as the full path to `bin/km` or through a variable it set (`$KM repin`), and the command text also turns up in descriptions, commit messages and `echo`s, so a match on the Bash input passes when km never started and fails when it ran. Where a command prints several lines, the pattern accepts more than one of them (`km doctor:` or its closing line, `ERRORS:` or `WARNINGS:`), so output cut by `| head` or `| tail` usually still passes. A run whose output was thrown away (`>/dev/null`, `km sync --quiet` with nothing to do, a `| tail` that keeps only the findings under `WARNINGS:`) fails the grader, and so does a refused edit, promote or stub that forwards km validate's report: that is not a validate run of its own. A change to what one of these commands prints changes its grader too, and so does a change to how `claude plugin eval` writes a tool result into the trace (`"tool_use_result":` followed by the output as a JSON string, or by an object whose `stdout` comes first).

The git steps are graded by what git did too. `finds-the-branch-docs` (`pr`) matches a line git prints about the branch's doc, `inbox/thermal-derating.md`: its `--stat` line, its `diff --git` header, or its `--name-status`, `--numstat` or `--raw` line; it depends on the trace format like the `runs-km-*` graders. A bare path is not accepted, since `git ls-files`, `ls` and `grep -l` print it too, so a run that only used `git diff --name-only` fails. `removes-the-submodule` (`brains-list-remove`) checks the state the run leaves behind: `.git/index` no longer holds `brains/peer`. A removal passes however its output was handled (`-q`, a redirect, a pipe); a `git rm -n`, a `deinit` alone or a failed `git rm` fails. It relies on the index keeping full paths (index format 2 or 3, as `git init` writes it; format 4 or a split index would let it pass on any run).

Run from the plugin root: `claude plugin eval . --scaffold --no-publish --ablation none --allow-tools Bash Write Edit`; `--tag batch2` selects the nine dispatch cases, and the no-plugin baseline (`--ablation with-without`) is worth its cost only when a grader changes. `results/` is ignored.

Before merging a change under `skills/km/`, run the cases whose dispatch-table row it touches, all of them for a change to the core or the table. Put the results in the PR body, with the baseline where a grader changed. A case that fails with the new skill and passes with the old one is a regression: fix the skill, not the grader.
