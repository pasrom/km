# CONVENTIONS.md (<BRAIN>)

This file defines the rules every person and AI assistant follows in the **<BRAIN>**, <TEAM>'s
shared, served knowledge base. For frontmatter, [`schema.base.yaml`](schema.base.yaml) +
[`schema.local.yaml`](schema.local.yaml) are authoritative and enforced by
[`scripts/validate.py`](scripts/validate.py) (pre-commit + CI); the frontmatter block below is their
human summary.

## Access & reading model

- **One writer.** Only the maintainer commits to `main`; everyone else has **read** access to the
  repository and reads the markdown directly. Contributions come as a **fork PR** (the maintainer
  reviews and merges) or are **promoted** from a personal brain via `scripts/km_promote.py`. Because
  only the maintainer commits, git history shows the maintainer, not per-author activity; the
  `author` field records who authored the knowledge (provenance, not a performance metric).
- **Curated corpus, not a workshop.** The <BRAIN> holds finished, reviewed knowledge; drafts and
  half-thoughts stay in personal brains. `status` marks maturity: read `accepted` as current and
  authoritative, `review` as submitted, `draft` as work in progress.
- **"Served" set (optional AI feed).** A doc is served when it is on `main` **and** `status: accepted`
  **and** its `audience` is allowed. CI builds an optional per-audience bundle (`internal` /
  `customer`) as a filtered, machine-readable feed for AI/RAG; people just read the repo.
- **Uphill-only:** a served doc links only to served or external targets, never into a personal
  brain. Personal brains may link **up** to the <BRAIN>.

## Folder structure

| Folder | Purpose |
|--------|---------|
<FOLDER_ROWS>

**Mechanical placement rule** (decides where a doc goes, no debate):
<PLACEMENT_RULES>

There is no `inbox/` in the served repo, unsorted intake stays in a personal brain or a draft PR.
Each folder has an `_index.md`. Its `## Documents` list is generated by `scripts/gen_index.py`
(the folder's docs plus a link to each subfolder's `_index.md`) and checked in CI: do not hand-edit
that list. The frontmatter and intro above it are hand-written, and so is a new folder's
`_index.md` itself: create it with a `description:` and an empty `## Documents` heading, then run
the script. The root `_index.md` lists the top-level folders the same way.

## Frontmatter schema

Every markdown file (except `CLAUDE.md`, `README.md`, `CONVENTIONS.md`, `SKILL.md`, and generated
`_index.md`) has YAML frontmatter:

```yaml
---
type: <note|concept|decision|transcript|artifact|summary|reference|verbatim-block>  # required
title: "Descriptive title"                          # required
timestamp: 2026-01-15                                # required (ISO-8601)
author: <initials>                                   # required, the real author, not the committer
status: <draft|review|accepted|superseded|obsolete>  # required
audience: <internal|customer>                        # required on served docs
tags: [tag1, tag2]                                   # required
language: <en|de>                                    # required on served docs
# Optional:
description: "One-sentence summary."
owner: <initials>                                    # responsible for keeping it true (staleness)
review_by: 2027-01-15                                # required once accepted
ticket: ABC-123                                      # provenance to the work item this doc came from
resource: "https://…"                               # URI of an external asset (datasheet/repo/tracker)
project: <name>
supersedes: <path.md>
superseded_by: <path.md>
related: [path1.md, path2.md]                        # repo-root-relative
sources: [path.md@abc1234]                           # required for type: summary
translates: <path.md@abc1234>                        # linked translation source
---
```

On promote, `author` resolves `--author` > source frontmatter > `author_default` (in
`schema.local.yaml`). The git committer is separate from `author` (the knowledge's originator).

## Document types

| Type | Purpose |
|------|---------|
| `concept` | Ideas, designs, evaluations, architecture (Problem → Solution → Implementation) |
| `decision` | Architecture Decision Record (Context → Options → Decision → Rationale) |
| `note` | Unstructured notes, observations |
| `transcript` | Meeting transcripts (Summary → Decisions → Actions → Raw) |
| `artifact` | Deliverables, specs, formal documents |
| `summary` | AI-generated summaries (with pinned `sources:`) |
| `reference` | Reference material, glossaries, how-tos |
| `verbatim-block` | Approved prose reused **verbatim** in customer material, change only via supersede |

## Status lifecycle

```
draft → review → accepted → superseded | obsolete
```

- `accepted` = reviewed, current, in the served set. Requires `owner` + `review_by`.
- CI **demotes** an `accepted` doc back to `review` when its `review_by` lapses, so it drops out of
  the served set automatically. Staleness is prevented, not just warned. An accepted doc that links
  to a demoted one then fails the gate; the weekly run turns red so the maintainer re-reviews either.
- Superseded/obsolete docs are **never deleted**; set `superseded_by:` when replacing.

## Naming

- Topics / concepts: `kebab-case.md`.
- Dated docs: `YYYY-MM-DD-kebab-case.md`.
- Decisions: `<ticket>-kebab-case.md` or `YYYY-MM-DD-kebab-case.md` (never a bare `NNN-` prefix, it
  collides under concurrent PRs).
- Folders: `kebab-case/`.

## Audience & language

- `audience: customer` docs are held to stricter rules (no internal symbol names, file paths, or
  build specifics; the gate scans them for forbidden terms and external emails). `internal` docs
  keep full implementation detail.
- Frontmatter (`title` / `description` / `tags`) is **English**; the body is in its declared
  `language`. `verbatim-block`s are paired per language via `translates:`; an accepted doc whose
  `translates:` source has moved past the pinned hash should be re-reviewed.

## What the <BRAIN> is NOT

- **No formal work products under configuration management** (requirements, safety cases,
  traceability): those live in the product repositories with their baselines; the brain holds
  *knowledge about* them and links out via `resource:`.
- **No binaries** (images / video / PDF / `.eml` / `.docx`) beyond a small size, reference an
  external store via `resource:` instead.
- **No copies of standards texts** or third-party documents.

## Enforcement

Enabled in `schema.local.yaml`: the **gate** (`secret` / `leak` / `bergab` / `freshness`),
**`check_index`** (navigation completeness), and **`author_default`**. Run `scripts/validate.py`
(pre-commit + CI); warnings never block, errors do. CI also fails when an `_index.md` Documents list
is stale or a folder with something to list has no `_index.md` (`scripts/gen_index.py --check`).

## Cross-references & git

- Relative markdown links in bodies; `related:` / `supersedes:` / `superseded_by:` use
  **repo-root-relative** paths. Never duplicate content, link.
- Conventional Commits `type(scope): description`; the PR title carries the ticket key. Work on a
  branch named by the ticket key; `main` is protected by the single-writer permission model.
