# CONVENTIONS.md (<BRAIN>)

This file defines the rules every person and AI assistant follows in the **<BRAIN>**, <TEAM>'s shared, served knowledge base. For frontmatter, [km's base schema](https://github.com/pasrom/km/blob/<KM_SHA>/src/km/schema.base.yaml) (km <KM_VERSION>) + [`schema.local.yaml`](schema.local.yaml) are authoritative and enforced by `km validate` (pre-commit + CI); the frontmatter block below is their human summary.

## Access & reading model

- **One merger.** Only the maintainer merges to `main`; everyone else has **read** access to the repository and reads the markdown directly. Contributions come as a **pull request** (the maintainer reviews and merges) or are **promoted** from a personal brain via `km promote`. Git history and pull requests show each contributor; they serve provenance, never per-person analysis. The `author` field records who authored the knowledge.
- **No direct push to `main`, the maintainer included.** `main` changes only by merging a pull request (rebase merge). There are two exceptions: the first push into the empty repository, which creates `main`, and the weekly staleness run, which commits its demotions to `main` itself. The pre-commit hook refuses a commit on `main`; where the host does not enforce the rule, the main-guard workflow fails and opens an issue for any commit on `main` that no merged pull request contains.
- **Curated corpus, not a workshop.** The <BRAIN> holds finished, reviewed knowledge; drafts and half-thoughts stay in personal brains. `status` marks maturity: read `accepted` as current and authoritative, `review` as submitted, `draft` as work in progress.
- **"Served" set (optional AI feed).** A doc is served when it is on `main` **and** `status: accepted` **and** its `audience` is allowed. CI builds an optional per-audience bundle (`internal` / `customer`) as a filtered, machine-readable feed for AI/RAG; people just read the repo.
- **Uphill-only:** a served doc links only to served or external targets, never into a personal brain. Personal brains may link **up** to the <BRAIN>.

There is no `inbox/` in the served repo, unsorted intake stays in a personal brain or a draft PR. Each folder has an `_index.md`. Its `## Documents` list is generated by `km gen-index` (the folder's docs plus a link to each subfolder's `_index.md`) and checked in CI: do not hand-edit that list. The root `_index.md` lists the top-level folders the same way.

## Frontmatter schema

Every markdown file (except `CLAUDE.md`, `README.md`, `CONVENTIONS.md`, `SKILL.md`, and generated `_index.md`) has YAML frontmatter:

```yaml
---
type: <note|concept|decision|transcript|artifact|summary|reference|verbatim-block>  # required
title: "Descriptive title"                          # required
timestamp: 2026-01-15                                # required (ISO-8601)
author: <initials>                                   # required, the real author, not the committer
status: <draft|review|accepted|superseded|obsolete>  # required
audience: <internal|customer>                        # required on served docs
tags: [tag1, tag2]                                   # required
language: <en|de>                                    # required on served docs
# Optional:
description: "One-sentence summary."
owner: <initials>                                    # responsible for keeping it true (staleness); from the roster, if set
review_by: 2027-01-15                                # required once accepted, unless the type does not expire
approval: <human|ai>                                 # who may sign off; unset = approval_default (see Status lifecycle)
approved_by: <initials | "ai:<model>">               # set by `km approve`, with approved_at and approved_digest
reviewed_by: ["<reviewer or model> <date> (PR #N)"]  # pre-reviews, not an approval
ticket: ABC-123                                      # provenance to the work item this doc came from
resource: "https://…"                               # URI of an external asset (datasheet/repo/tracker)
project: <name>
supersedes: <path.md>
superseded_by: <path.md>
related: [path1.md, path2.md]                        # repo-root-relative
sources: [path.md@abc1234def0]                       # `km repin` writes it; required for type: summary
translates: <path.md@abc1234def0>                    # linked translation source; `km repin` writes it
cites:                                               # external files (SharePoint, OneDrive); `km cite add` writes it
- url: https://example.sharepoint.com/sites/Example/Shared%20Documents/report.pdf
  sha256: <64 hex digits of the file's bytes>
  retrieved: 2026-11-04
---
```

On promote, `author` resolves `--author` > source frontmatter > `author_default` (in `schema.local.yaml`). The git committer is separate from `author` (the knowledge's originator). A new doc's `owner` resolves `--owner` > source frontmatter > its `author`; `--replace` keeps the owner the doc has. Where `schema.local.yaml` sets a roster (`owners: [AB, CD]`), a doc not superseded or obsolete that names an owner must name one from it (the roster does not require an owner; `status_rules` such as `review_requires: [owner]` do): when someone leaves, reassign their docs in the same pull request that takes them off the roster.

## Document types

| Type | Purpose |
|------|---------|
| `concept` | Ideas, designs, evaluations, architecture (Problem → Solution → Implementation) |
| `decision` | Architecture Decision Record (Context → Options → Decision → Rationale) |
| `note` | Unstructured notes, observations |
| `transcript` | Meeting transcripts (Summary → Decisions → Actions → Raw) |
| `artifact` | Deliverables, specs, formal documents |
| `summary` | AI-generated summaries (with pinned `sources:`) |
| `reference` | Reference material, glossaries, how-tos |
| `verbatim-block` | Approved prose reused **verbatim** in customer material, change only via supersede |

## Status lifecycle

```
draft → review → accepted → superseded | obsolete
```

- `accepted` = reviewed, current, in the served set. Requires `owner` + `review_by`; `km approve` and `km promote` set `review_by` when it is missing, to the type's default: 365 days for `reference` and `concept`, 182 days for `note`, `summary` and any other type. A `decision` (superseded, not stale), `transcript`, `verbatim-block` or `artifact` (fixed records) does not expire: it needs no `review_by` and gets none. One it already carries is ignored: it is never demoted for it. `review_by_default` in `schema.local.yaml` overrides single types, in days or `null` for no expiry (e.g. `review_by_default: {note: 90}`).
- Sign-off is `km approve <doc> --by <initials>`, after the author's review (`/km review`) and before the merge: on a pull request CI fails a changed doc that is not signed off (`km validate --signoff-since`), and an `accepted` or `approved_by` set by hand is not a sign-off. With `approval: ai`, or `approval_default: ai` in `schema.local.yaml` and no `approval` field, an AI review alone may sign off (`--by ai:<model>`); otherwise a person must. Only docs marked `audience: internal` can take an AI sign-off: customer-facing docs, any other audience, docs without an audience and verbatim-blocks always need a person.
- An approval covers the content it saw: `km approve` records a digest of the body and the content fields (title, description, type, audience and the like; not tags, dates, owners, links, pins or cites). A change to that content afterwards fails `km validate`, so the commit that makes it also sends the doc back to review (`km demote <doc>`); the approval follows after review, in a commit of its own (`km approve <doc> --by <initials>`). Quote versions and numbers in those fields (`valid_for: "1.10"`).
- CI **demotes** an `accepted` doc back to `review` when its `review_by` lapses, so it drops out of the served set automatically. Staleness is prevented, not just warned. An accepted doc that links to a demoted one then fails the gate; the weekly run turns red so the maintainer re-reviews either.
- Superseded/obsolete docs are **never deleted**; set `superseded_by:` when replacing.

## Naming

- Topics / concepts: `kebab-case.md`.
- Dated docs: `YYYY-MM-DD-kebab-case.md`.
- Decisions: `<ticket>-kebab-case.md` or `YYYY-MM-DD-kebab-case.md` (never a bare `NNN-` prefix, it collides under concurrent PRs).

## Audience & language

- `audience: customer` docs are held to stricter rules (no internal symbol names, file paths, or build specifics; the gate scans them for forbidden terms and external emails). `internal` docs keep full implementation detail.
- Frontmatter (`title` / `description` / `tags`) is **English**; the body is in its declared `language`. `verbatim-block`s are paired per language via `translates:`; when a `translates:` or `sources:` source changes after its pin, `km validate` reports `pin:stale`: re-review the doc, then `km repin` it (an accepted doc goes back to review for a new sign-off). `km repin` pins the source's content (its blob), which survives a rebase or squash merge; a pin to a commit set on a PR branch does not.
- A SharePoint or OneDrive file a doc relies on goes under `cites:`, written by `km cite add <doc> <url> --file <synced copy>` (the sha256 of the copy, and the date). `km cites check --dir "<synced library>=https://<host>/sites/<site>/<library>"` maps the library to its URL and reports a cited file that changed as `stale`: re-review the doc, then `km repin --cites` it (an accepted doc goes back to review, as it does when a new file is cited). Cite the team-site copy, not a personal OneDrive. km rewrites the `cites:` block whole: comments inside it are dropped.

## What the <BRAIN> is NOT

- **No formal work products under configuration management** (requirements, safety cases, traceability): those live in the product repositories with their baselines; the brain holds *knowledge about* them and links out via `resource:`.
- **No binaries** (images / video / PDF / `.eml` / `.docx`) beyond a small size, reference an external store via `resource:` instead.
- **No generated file without its source**: an image or diagram made from a source that can be rerun (a script, a `.drawio` file, small input data) is committed with that source in the same folder, and the doc says how to regenerate it, so the next change edits the source instead of redrawing the output. A draw.io export with the diagram embedded is its own source (the doc says to edit it in draw.io); a screenshot or an instrument capture has none. Large input data, or data kept out of git on purpose, stays in an external store: the doc names where it is (`resource:`).
- **No copies of standards texts** or third-party documents.

## Enforcement

Enabled in `schema.local.yaml`: the **gate** (`secret` / `leak` / `bergab` / `freshness`), **`check_index`** (navigation completeness), and **`author_default`**. Run `km validate` (pre-commit + CI); warnings never block, errors do. CI also fails when an `_index.md` Documents list is stale or a folder with something to list has no `_index.md` (`km gen-index --check`).

## Cross-references & git

- Relative markdown links in bodies; `related:` / `supersedes:` / `superseded_by:` use **repo-root-relative** paths. Never duplicate content, link.
- Conventional Commits `type(scope): description`; the PR title carries the ticket key. Work on a branch named by the ticket key; `main` changes only through a merged pull request.
