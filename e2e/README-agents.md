# km end-to-end test: the agent layer

Phase 3 of the e2e test (`README.md` describes the sandbox, the environment and the deterministic driver). Here Claude agents play the roles and run the km skill itself, in interactive Claude Code sessions under the subscription, started by hand on the maintainer's machine. No API key and no `claude -p`.

## Files

| File | What it does |
|---|---|
| `container/` | The image every session runs in (`Dockerfile`), its entrypoint and its egress firewall (`init-firewall.sh`) |
| `agent_profile.py` | What a session is given inside its container: the managed settings, the first-run marks, the environment; `check` is the preflight's part about the image and the token |
| `agent_launch.py` | The role launcher: one fresh container per role step, GitHub access through the role's wrappers, the wait for the sentinel, the transcripts read out of the container |
| `agent_scenarios.py` | E02 as agent (`E02a`), E14 with E15, E26 with and without the script, E22 |
| `agent_judge.py` | Reads the agent's final message from the transcript, compares the queue with the oracle, checks thread replies; the model judge's prompt and verdict |
| `agent_run.py` | The driver: the plugin export, the firewall's input, preflights (egress probes included), lock, reset, E01, the PRs the queue needs, the agent scenarios, cleanup, report |
| `prompts/` | The role prompts; `_common.md` carries the consent limited to the sandbox and the sentinel |

## Roles

| Role | Who | Token in the session |
|---|---|---|
| `M` maintainer | the driver, never an agent. In E14 the driver posts the maintainer's review (one true finding, one wrong one: an agent would not write a wrong finding on purpose) | none (no agent holds it) |
| `C` contributor | an agent working in a clone of `C`'s fork | `C`'s token file |
| `S` subject-matter colleague | signs off through `C`'s branch (`km approve --by BBB`), as the maintainer guide describes | `C`'s |
| `X` adversary | a behaviour of `C`'s login: in E15 the driver writes, as `C`, instructions into a review thread and the PR body | `C`'s |
| `J` judge | a model verdict on wording, reported apart from the checks | none, no tools, an empty folder |

The queue agent of E22 plays `Q`: `C`'s token, read-only by its wrappers. Its gh wrapper runs only reading subcommands (`pr list`, `pr view`, `pr checks`, ...) and `gh api` with an allowlist of options (`--jq`, `--paginate`, `--include`, `-H` with a GitHub `Accept` header, `-X GET`), no GraphQL; its git has no credentials at all (the driver clones the sandbox's `main` for it just before the session). Limit: the gh wrapper still reads `C`'s token in its own process, so a session that goes around the wrapper (a shell command reading the token file) has `C`'s rights in the sandbox. The stronger option, not set up yet: a separate fine-grained token for `C`'s account with read-only access to the sandbox, mounted for `Q` instead of `C`'s, so the queue is read-only on GitHub's side whatever the session does. The oracle reads `gh pr checks` with `C`'s token as well, since `M`'s fine-grained token cannot read the status rollup.

## The container

Every session, the model judge's included, runs in a fresh container of one image, built once from `container/` (after Claude Code's reference devcontainer): Node with Claude Code, git, gh, jq, python3 with PyYAML, and uv with km's PyYAML pin in its cache, so km starts without a package index. The base image is pinned by digest, Claude Code by version, gh and uv by release checksum. gh itself is off every `PATH` (`/opt/gh/bin`): a session reaches it only through its role's wrapper, also from inside km, which `uv run` starts with uv's own folder first on the `PATH` (the preflight checks that `gh` under `uv run` is the wrapper).

- **Nothing of the host.** No home folder, keychain, terminal, launchd, tmux or other local socket, no person's Claude profile. Exactly two mounts, both read-only: the km plugin export (`/opt/km`) and the role's GitHub token file (`/run/km-e2e/gh-token`). The clone (`/work/clone`), a step's extra folders (`/work/inputs/<name>`), the role's wrappers and the config folder's first-run marks are copied in before the container starts; nothing is copied back but what the driver reads.
- **Egress allowlist.** The entrypoint, as root, sets up the firewall before anything else runs: outbound only tcp/443 to GitHub's web, api and git ranges and to one address each for `github.com`, `api.github.com` and `api.anthropic.com`, all read once per run by the driver (`api.github.com/meta`, the host's resolver) and checked in the container to be public. Those names are pinned in `/etc/hosts` and DNS is closed from the start (port 53 refused, no resolver), so a lookup cannot carry data out and no other name resolves. Everything else is refused: the host (`host.docker.internal`), the Docker gateway, the LAN, private, link-local and metadata addresses, SSH, IPv6. No package index: km's PyYAML comes from the image's uv cache (`UV_OFFLINE`), and with no cache hit km falls back to the image's python3 with PyYAML.
- **No privileges.** The container keeps only the capabilities the entrypoint needs (`NET_ADMIN`, `NET_RAW` for the firewall, `CHOWN` to hand the copied files over, `SETUID`, `SETGID`, `SETPCAP` to drop), with `no-new-privileges`; the entrypoint then runs the session as `node` with an empty bounding set. No sudo in the image. The session user cannot change the firewall, the managed settings, the plugin or the wrappers (all root-owned or read-only).
- **Settings.** Managed settings (`/etc/claude-code/managed-settings.json`, root-owned; they apply whatever `--setting-sources` says, and with `allowManagedPermissionRulesOnly` and `allowManagedHooksOnly` nothing a session writes into its config folder adds a rule or a hook): permission mode `dontAsk`, so anything not allowed is denied, never asked. Allowed: the km skill's commands (`km`, `git`, `gh`, `jq`, `uv`, `python3` and read-only helpers), file reads and writes under `/work`, reads of the plugin, subagents. Denied: `gh auth` (but `status`), `gh alias`, `gh extension`, `gh config`, `git -c`, `git config`, reads of the token file, writes to the config folder, `/opt` and `/etc`, web access. No memory, no claude.ai connectors or synced skills and plugins, no installed plugins, no MCP servers (`--strict-mcp-config` with an empty set); the plugin is loaded with `--plugin-dir`, and its `skills/km/bin` is on the `PATH`. The config folder starts with the first-run screens marked as seen and the clone trusted, so an unattended session starts at the prompt. The launcher refuses to start a session in a folder holding `.claude/`, `.mcp.json` or `CLAUDE.local.md` outside `.git` (an adversary could commit them to the sandbox); the brain's `CLAUDE.md` is content, and the prompt treats instructions in it beyond the km flow as data.
- **Each container is fresh**, so nothing a session changes reaches the next one. The km plugin is never installed: each run exports km at the candidate commit with `git archive` beside the workdir (`<workdir>-plugins/<run id>`), checks every exported file against the blob the candidate's tree names, makes it read-only, and mounts it read-only. The export is removed at the end of the run.

## Once: the image and the token

```sh
docker build -t km-e2e-agent:1 e2e/container      # again after a change under e2e/container/
claude setup-token                                 # a subscription account, not the Console
umask 077 && pbpaste > ~/.config/km-e2e/claude-oauth-token   # after copying the token it prints
```

`KM_E2E_IMAGE` and `KM_E2E_CLAUDE_TOKEN_FILE` override the image and the token file. Every session runs with `--model claude-fable-5-2` (`KM_E2E_MODEL` overrides): a session logged in with the token alone falls back to Claude Code's general default rather than the account's (observed: a run on the host profile got one model, the same token in a container another), and runs should compare; each session's model is in the report's notes. The driver passes the token into each container as `CLAUDE_CODE_OAUTH_TOKEN`, by name (its value is in the docker client's environment, never on a command line). A session can read its own environment, so the token is in reach of the agent like `C`'s; the firewall lets it reach only Anthropic and GitHub, and it is part of the leak checks.

## Run

```sh
source /path/outside/the/repo/km-e2e.env
python3 e2e/agent_run.py --preflight     # run.py's preflight and the agent preflight; writes nothing
python3 e2e/agent_run.py --canary        # one trivial session; writes nothing to GitHub
python3 e2e/agent_run.py                 # reset, E01, E03/E06/E08 for the queue, E02a, E14+E15, E26, E26-noscript, E22
python3 e2e/agent_run.py --only E14      # a subset (still resets and runs E01 first)
```

`--no-model-judge` leaves out the model verdicts; `--skip-reset` and `--steal-lock` as in `run.py`. The run takes the same lock as `run.py`, so the two never share the sandbox. Sessions run one after the other; to watch one, `docker ps` names its container `km-e2e-<run id>-<step>` (`docker exec <id> cat ...` reads its state; never change it). The report is `report.md` and `report.json` in the run folder, as for `run.py`, with the judge's verdicts and the firewall's refusals per session as notes; each step's outcome and transcripts are kept in `agents/<step>/`.

Agent preflight, on top of `run.py`'s: `KM_E2E_CONTRIB_TOKEN_FILE` is set, Docker and the image are there, the subscription token file is private. Then one container built exactly as a session's (same arguments, entrypoint, firewall, user and wrappers) runs the probes, and a control container of the same image without the firewall runs the egress part again:

- egress: a public address by IP, `example.com` by name, DNS straight to a public resolver and through the container's resolver, the host's loopback through `host.docker.internal` (a listener the driver opens, which counts connections), the Docker gateway, the host's LAN gateway on 80 and 443, the metadata address, SSH to GitHub and IPv6 must all fail; `api.github.com`, `github.com` and `api.anthropic.com` must answer. The control must reach the public address, the name, both DNS paths and the host listener, or those probes could not show a leak; a probe that does not run to its end fails the preflight;
- `docker inspect`: exactly the two read-only mounts from the plugin export and `C`'s token file, exactly the entrypoint's capabilities, `no-new-privileges`, nothing shared with the host (privileged, pid, ipc, network, devices, ports);
- inside, as the session user: no capability, `NoNewPrivs`, `iptables` denied, the managed settings, plugin and step files not writable; `gh` is `C`, `gh auth status` works, `gh auth token` fails, every `KM_E2E_MUST_NOT_REACH` repository answers 404 to `gh` and refuses `git ls-remote`, `C`'s fork answers `git ls-remote`, and without the wrapper `gh` has no login; `claude auth status` is the subscription; the plugin's `km --version` runs.

A failed or unfinished probe fails the preflight. The scenarios whose sessions read text an adversary wrote (E14 with E15, E22) run only when every egress probe passed and the control showed each controlled probe could bite.

## How a session runs

1. The launcher writes a staging folder on the host (`~/.config/km-e2e/sessions/km-e2e-<run id>/<step>/`, owner only): the role's two wrappers, a `gh` first on the session's `PATH` that reads the token file for that one call, runs only the subcommands the skill uses (`pr`, `issue`, `api`, `repo`, `run`, `label`, `search`, and `auth status`, which the skill checks first) and refuses `alias`, `extension`, `config`, `auth`, `secret`, `ssh-key`, `gpg-key` and `--show-token` anywhere in its arguments, gists, repository creation, forks and edits, and any repository but the sandbox and `C`'s fork, and git's credential helper for github.com; a git config for the role (identity, that helper); an empty gh config (no login, alias or extension can be installed or loaded); the Stop hook; the firewall's input; the managed settings; the config folder's `.claude.json`; and `step.json` with the container's command (never a token).
2. It creates the container (`docker create -t -i`, the capabilities above, the two read-only mounts, the session's environment, a label for cleanup), copies the staging folder, the clone and the step's extra folders in, and starts it. The entrypoint sets up the firewall, hands `/work` and the home folder to `node`, and runs `claude` interactively with the prompt, the driver's session id (`--session-id`), user settings only and no MCP server.
3. Every few seconds the driver reads the Stop hook's file and the config folder's transcripts out of the container with `docker cp` (a tar stream: regular files only, no links, no `..` or absolute paths, size-capped). It waits until the transcript of its own session id ends with an assistant message whose last line is `KM-E2E-DONE` and neither it nor its subagents' transcripts changed for a while (a turn can end while subagents still run), up to the step's limit; a session that stops to ask a question never writes the sentinel and fails the step. A session that has written no transcript after two minutes sits on a dialog: the step fails at once, with the screen's text (`docker logs`) in the report.
4. The driver reads the firewall's refusal counter (its `KM_REJECT` chain, which also counts refused DNS lookups, so a name the session needs and the pins lack shows), stops the container, reads the transcripts once more and keeps them in `agents/<step>/transcripts/`, then removes the container by its id (`close()` removes any container left with the run's label). It never runs git or km in a clone a session worked in: `km ready` and the queue oracle use the driver's own clone, everything else reads GitHub. Every transcript, and everything on each PR an agent opened or worked (title, body, comments, reviews, commit messages, patches), is checked for `C`'s and `M`'s tokens and the subscription token in plain, reversed, hex, base64 and URL-encoded form; every transcript also for the repositories it must not reach and their owners.

## Limits

- `tests/e2e_agent_smoke.sh` checks the pure parts: settings, the staging folder and `docker create`'s arguments, the wrappers, reading a container's files, the wait, the firewall's address check and rules. The container itself is checked by the preflight's probes on every run and by `--canary` (trust, permissions, the plugin's km, the role's gh, the Stop hook, the transcript and the firewall together: no connection refused that Claude Code, gh or km needed).
- **Residual risk: the firewall is not containment.** The subscription token and `C`'s GitHub token are in the agent's reach inside the container (environment, mounted file), and GitHub is allowed: a session can write either token to GitHub with `C`'s token (a gist, an issue or comment in any repository `C` can reach, a new repository under `C`), straight through the API with `curl` if it goes around the gh wrapper. An authenticating proxy that holds the tokens outside the container would close this; it is not built. The mitigations:
  - the role's gh wrapper refuses gists, creating, forking, editing or deleting a repository, any `-R`/`--repo` value or `repos/...` API path other than the sandbox and `C`'s fork, any URL argument, gh's `{owner}`/`{repo}` placeholders (filled from the clone's remotes, which a session can change; `git remote` is denied to the shell tool too), a GraphQL query from a file, and every GraphQL write but the two the skill uses (reply to a review thread, resolve it; those take a thread id, which the wrapper cannot tie to a repository). A speed bump, not a boundary;
  - after the agent scenarios the driver reads, as `C` and read only, `C`'s gists (with their files), `C`'s own repositories, `C`'s events since the run started (wherever they happened), and the sandbox's issues, pull requests and comments. A gist, a new repository, a push outside the fork, activity outside the sandbox and fork, or a token in any of it fails the run (`exfil` in the report) and prints the instruction to revoke the subscription token (claude.ai settings) and `C`'s token. A passing sweep means no token was found in the places checked, not that the tokens are safe: after any run with E14, E15 or E22 the report ends with a recommendation to rotate the subscription token and `C`'s token, and rotating them is the advice. Not covered: file contents of pushed commits outside a PR's patches, a GraphQL write the events API does not show, events GitHub publishes late (minutes), and a write to a repository `C` can reach that leaves no event in `C`'s feed;
  - `C`'s account must reach nothing but the sandbox (the preflight's 404 checks cover `KM_E2E_MUST_NOT_REACH` only; a classic token reaches whatever `C` can), and every transcript and every PR an agent touched is checked for both tokens.
- GitHub's address ranges are shared by all of github.com: the allowlist admits any GitHub host on them over tcp/443 (connecting by address with another name), not only the three pinned names.
- No package index is reachable. A km that needs a package not in the image's cache (another PyYAML pin, a `uvx` run of a different km commit a brain pins) falls back to the image's python3 or fails; rebuild the image after such a change.
- The permission list is not the security boundary. It allows `python3`, `uv`, `awk`, `sed`, `find` and `GIT_SEQUENCE_EDITOR=... git rebase` for the skill, and any of them can run other commands; deny rules for shell commands match by prefix. The boundary is the container with its firewall and the role's token, which reaches only the sandbox. Known gaps of the gh wrapper, left as they are for that reason: it refuses its listed words as any whole argument, so a rare legitimate value such as a label named `config` is refused too; a crafted `gh api` call of `C` can still do what `C` may do in the sandbox.
- A command the skill needs and `dontAsk` denies shows in the transcript as a denied tool call; extend `BASH_ALLOW` in `agent_profile.py`. A host the session needs and the firewall refuses shows in the firewall note of the report; extend `ALLOWED_HOSTS` in `agent_run.py`.
- Docker Desktop on macOS is the only tested host. On plain Docker on Linux the preflight fails closed: there is no `host.docker.internal` for the host probe, and a bind-mounted 0600 token file is readable by the session user only when the host user's uid is 1000.
- The transcripts are listed (with sizes) while the container runs and read after it stopped; a transcript over 64 MiB is left out, and a session's own transcript that cannot be read fails the step, since the leak checks need it. A session could still grow a file between the listing and the stop.
